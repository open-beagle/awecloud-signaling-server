# Tailscale 升级方案设计

## 1. 升级必要性

### 1.1 当前架构痛点

| 问题         | 描述                                              |
| ------------ | ------------------------------------------------- |
| **流量绕行** | 办公网络访问公司内网 K8s，流量需绕行互联网 Server |
| **带宽瓶颈** | 所有流量经过公网 Server 中继，带宽受限            |
| **延迟较高** | 内网 → 公网 → 内网，增加不必要的网络跳数          |
| **成本浪费** | 同一局域网内的访问也消耗公网带宽                  |

### 1.2 Tailscale 优势

| 优势               | 描述                             |
| ------------------ | -------------------------------- |
| **智能路由**       | 同网段 P2P 直连，跨网段才走中继  |
| **WireGuard 加密** | 现代化加密协议，性能优异         |
| **NAT 穿透**       | 自动穿透各种 NAT，成功率高       |
| **虚拟组网**       | 所有设备在同一虚拟网络，互相可达 |
| **抗封锁**         | 流量特征不明显，DERP 回退 HTTPS  |

### 1.3 流量特征对比

| 特性           | FRP                     | Tailscale             |
| -------------- | ----------------------- | --------------------- |
| **协议**       | 自定义协议，特征明显    | WireGuard (标准 UDP)  |
| **流量伪装**   | WebSocket 可被 DPI 识别 | UDP 流量，难以区分    |
| **端口**       | 固定端口 7000           | 动态端口 41641        |
| **DPI 检测**   | 容易被识别和封锁        | 较难识别              |
| **回退机制**   | 无                      | DERP (HTTPS 443)      |
| **防火墙友好** | ❌ 易被企业防火墙拦截   | ✅ HTTPS 回退难被封锁 |

**Tailscale 穿透策略**：

1. UDP 直连 (WireGuard 41641) → 最快，大多数网络可用
2. UDP 穿透 (STUN/ICE) → NAT 穿透，成功率高
3. HTTPS 中继 (DERP 443) → 最稳定，与正常 HTTPS 流量无异

**为什么 DERP 难被封锁**：

- 使用标准 HTTPS 端口 443
- TLS 加密，流量与普通网页访问无异
- 自建 DERP 使用自己的域名，完全像正常网站
- 无法通过 DPI 区分是 DERP 还是普通 HTTPS

### 1.4 Tailscale vs Coturn 对比

Coturn 是标准的 STUN/TURN 服务器实现，与 Tailscale 的 DERP 有本质区别：

#### 协议和架构对比

| 特性               | Coturn (STUN/TURN)     | Tailscale (WireGuard + DERP) |
| ------------------ | ---------------------- | ---------------------------- |
| **协议标准**       | RFC 5389/5766 标准协议 | 私有协议 (基于 WireGuard)    |
| **穿透方式**       | STUN 探测 + TURN 中继  | STUN 探测 + DERP 中继        |
| **加密**           | DTLS (可选)            | WireGuard (始终加密)         |
| **中继效率**       | TURN 中继开销大        | DERP 中继更轻量              |
| **TCP/HTTPS 回退** | 支持但效率低           | DERP over HTTPS 优化过       |
| **组网能力**       | 仅点对点               | 虚拟网络 + 子网路由          |
| **管理复杂度**     | 需要自己实现信令       | Headscale 一体化             |

#### 中继机制对比

**Coturn TURN 中继的工作方式**：

```txt
Client A ──────► TURN Server ──────► Client B
                     │
            ┌────────┴────────┐
            │ 1. 分配中继地址   │
            │ 2. 解包数据      │
            │ 3. 重新封包      │
            │ 4. 转发到目标    │
            └─────────────────┘

问题：
- 每个连接需要分配中继地址（资源消耗）
- 所有数据包都要经过 TURN 解包/重新封包（CPU 开销）
- TCP/TLS 模式下效率更低（TCP over TCP 问题）
```

**Tailscale DERP 中继的工作方式**：

```txt
Client A ──────► DERP Server ──────► Client B
                     │
            ┌────────┴────────┐
            │ 简单包转发       │
            │ 无需分配地址     │
            │ 无需解包重封     │
            │ WebSocket 长连接 │
            └─────────────────┘

优势：
- DERP 是简单的包转发，不做复杂处理
- 专为 WireGuard 设计，开销极小
- HTTPS 模式下也保持高效（WebSocket 长连接复用）
```

#### 性能对比

| 场景               | Coturn TURN | Tailscale DERP |
| ------------------ | ----------- | -------------- |
| **UDP 中继延迟**   | +5-10ms     | +2-5ms         |
| **TCP 中继延迟**   | +20-50ms    | +5-15ms        |
| **HTTPS 中继延迟** | +50-100ms   | +10-30ms       |
| **中继带宽开销**   | ~20%        | ~5%            |

#### 为什么 Tailscale 更适合

1. **一体化方案**：Headscale = 控制平面 + STUN + DERP，不需要单独部署 Coturn
2. **子网路由**：Coturn 只能点对点，Tailscale 可以路由整个内网网段
3. **始终加密**：WireGuard 加密是强制的，Coturn 的 DTLS 是可选的
4. **更好的回退**：DERP over HTTPS 比 TURN over TLS 效率高很多
5. **无状态转发**：DERP 不需要维护复杂的中继状态，更易扩展

#### 混合方案（如果已有 Coturn）

如果已经部署了 Coturn，可以考虑：

- Tailscale 用于组网和管理
- 自建 DERP 服务器（Tailscale 支持自建）
- Coturn 可以作为备用 STUN 服务器（仅用于 NAT 探测）

### 1.5 典型场景对比

**场景：办公网络访问公司内网 K8S**

| 方案       | 路径                                | 延迟  |
| ---------- | ----------------------------------- | ----- |
| FRP (当前) | Desktop → 公网 Server → Agent → K8S | ~50ms |
| Tailscale  | Desktop → Agent → K8S (P2P 直连)    | ~2ms  |

## 3. 核心业务场景

### 3.1 业务场景总览

| 场景         | 描述                           | 访问方式             | 网段冲突风险 |
| ------------ | ------------------------------ | -------------------- | ------------ |
| Gateway 暴露 | 内网 HTTPS 网关暴露到互联网    | Tailscale IP + socat | 无           |
| 数据库调试   | 开发人员访问内网 MySQL/Redis   | Tailscale IP + socat | 无           |
| SSH 运维     | 运维人员访问内网服务器         | Tailscale IP + socat | 无           |
| 群晖 NAS     | Drive Client 同步（6690 端口） | Tailscale IP + socat | 无           |

**核心思路**：由于家里和公司都是 192.168.1.0/24 网段，不能使用子网路由。统一采用 Tailscale IP (100.64.x.x) + socat 端口代理模式，在公司 K8S 中部署 Tailscale Pod 作为代理网关。

### 3.2 场景一：Gateway 暴露

**需求**：将内网的 HTTPS 网关（如 Traefik/Nginx）暴露到互联网服务器。

**核心问题**：

- 互联网 Traefik 只能访问 Pod 网络（10.2.x.x）
- 公司网关在内网（192.168.1.x），无法直接路由
- 家里和公司都是 192.168.1.0/24 网段，不能用子网路由

**解决方案**：Tailscale IP (100.64.x.x) + Agent 内置 TCP 代理

#### IP 地址汇总

| 位置               | Pod IP (K8S 网络) | Tailscale IP | 内网 IP     |
| ------------------ | ----------------- | ------------ | ----------- |
| 互联网 Traefik Pod | 10.2.100.1        | -            | -           |
| 互联网 Agent       | 10.2.200.50       | 100.64.0.20  | -           |
| 公司 Agent         | 10.2.50.100       | 100.64.0.10  | -           |
| 内网网关           | -                 | -            | 192.168.1.1 |

#### 关键配置说明

**互联网侧 Agent 配置**：

Agent 内置 Tailscale + TCP 代理，通过 gRPC 从 Server 接收端口映射指令：

```txt
端口映射配置 (通过 Web 界面或 API 创建):
  - 名称: gateway-443
  - 监听端口: 443
  - 目标地址: 100.64.0.10:443 (公司 Agent 的 Tailscale IP)

Agent 内部处理:
  1. tsServer.Listen(":443")  // 在 Pod IP 上监听
  2. 接受连接后，tsServer.Dial("tcp", "100.64.0.10:443")
  3. 双向转发数据
```

**公司侧 Agent 配置**：

```txt
端口映射配置 (通过 Web 界面或 API 创建):
  - 名称: internal-gateway
  - 监听端口: 443
  - 目标地址: 192.168.1.1:443 (内网网关)

Agent 内部处理:
  1. tsServer.Listen(":443")  // 在 Tailscale IP 上监听
  2. 接受连接后，net.Dial("tcp", "192.168.1.1:443")
  3. 双向转发数据
```

**优势**：

- 单容器部署，无需 socat
- 通过 Web 界面动态管理端口映射
- 支持流量统计和连接数监控

#### 为什么这样设计

1. **避免网段冲突**：使用 Tailscale IP (100.64.x.x) 通信，不依赖内网 IP
2. **Pod 网络隔离**：互联网 Traefik 只需访问 Pod 网络，无需知道 Tailscale 细节
3. **灵活扩展**：同样模式可用于群晖、数据库等其他服务
4. **安全性**：流量全程 WireGuard 加密

### 3.3 场景二：数据库/Redis 调试

#### 为什么不能用子网路由

```txt
问题场景:
  家里网络: 192.168.1.0/24 (路由器分配)
  公司网络: 192.168.1.0/24 (相同网段)
```


### 3.7 网段冲突问题（重要）

**问题描述**：

- 家里网络：`192.168.1.0/24`
- 公司 K8S 节点：`192.168.1.0/24`（相同网段）
- 当 Desktop 在家访问公司内网时，路由会冲突

**冲突表现**：

- 访问 `192.168.1.100` 时，系统不知道是访问家里设备还是公司设备
- 可能导致连接失败或连接到错误的设备

**解决方案**：

**方案 A：使用 Tailscale IP 访问（推荐）**

每个设备加入 Tailscale 后会获得唯一的 100.64.x.x 地址：

- 公司群晖：`100.64.0.10`
- 公司数据库：`100.64.0.11`
- 使用 Tailscale IP 访问，不依赖内网 IP，避免冲突

配置方式：

- 群晖、数据库服务器等关键设备直接安装 Tailscale
- 或在 Headscale 中为 Agent 子网路由的设备分配固定 IP

**方案 B：使用 MagicDNS**

Tailscale 支持 MagicDNS，为每个设备分配域名：

- 公司群晖：`nas.ts.company.com`
- 公司数据库：`mysql.ts.company.com`
- 使用域名访问，自动解析到 Tailscale IP

**方案 C：规划不冲突的网段**

如果可以调整网络规划：

- 家里网络：`192.168.1.0/24`
- 公司网络：`10.0.0.0/8` 或 `172.16.0.0/12`
- 从根本上避免网段冲突

**方案 D：Split DNS（高级）**

配置 Tailscale 的 Split DNS：

- 访问 `*.company.internal` 时走 Tailscale
- 其他域名走本地 DNS
- 需要内网有 DNS 服务器

**建议**：

- 短期：使用 Tailscale IP 或 MagicDNS 访问关键服务
- 长期：规划不冲突的内网网段

### 3.8 组件说明

#### Headscale（控制平面）

Headscale 是 Tailscale 控制服务器的开源实现，负责：

- 设备注册和认证
- 密钥交换和分发
- 路由信息同步
- ACL 访问控制

**不经过数据流量，仅交换控制信息。**

#### DERP Server（中继服务）

DERP (Designated Encrypted Relay for Packets) 是备用中继：

- 当 P2P 穿透失败时使用
- 流量加密传输
- 可自建私有 DERP

#### Tailscale Client / tsnet

运行在每个节点上：

- Agent 节点（公司内网）：作为子网路由器
- Desktop 节点（办公网络/员工家里）：访问内网服务
- 自动 NAT 穿透和 P2P 连接

## 4. 单域名架构设计

### 4.1 域名和端口规划

所有服务通过单一域名 `https://signaling.your-domain.com` 对外提供：

```txt
https://signaling.your-domain.com
├── /                    → Server-Web      (业务 API + Web 管理)
├── /api/v1/...          → Server-Web      (RESTful API)
├── /grpc/...            → Server-Web      (gRPC)
├── /headscale/...       → Headscale       (控制平面 API)
├── /derp                → DERP Server     (中继，HTTPS)
└── /ts2021              → Headscale       (Tailscale 协议)

UDP:3479                 → DERP STUN       (NAT 探测，避开 Coturn 的 3478)
```

## 5. 三端嵌入方案

### 5.1 嵌入架构总览

Tailscale 基于 Go 开发，提供 `tsnet` 包用于嵌入，与 FRP 嵌入方式类似：

| 组件    | 原模块      | 新模块               | 嵌入方式         |
| ------- | ----------- | -------------------- | ---------------- |
| Server  | Server-Web  | Server-Web           | 保留不变         |
| Server  | Server-FRP  | Headscale API 客户端 | HTTP API 调用    |
| Server  | -           | DERP Server          | 可选嵌入         |
| Agent   | Agent-Web   | Agent-Web            | 保留不变         |
| Agent   | Agent-FRP   | tsnet                | 库嵌入，替换 FRP |
| Desktop | Desktop-Web | Desktop-Web          | 保留不变         |
| Desktop | Desktop-FRP | tsnet                | 库嵌入，替换 FRP |

### 5.2 Agent 嵌入说明

Agent 端使用 `tsnet.Server` 嵌入 Tailscale 客户端，并内置 TCP 代理功能，实现单容器完成所有工作。

**核心配置项**：

- `Hostname`: 使用 Agent 名称作为 Tailscale 主机名
- `Dir`: 状态存储目录，保存密钥和配置
- `ControlURL`: 指向 Headscale 控制平面（单域名 + /headscale 路径）
- `AuthKey`: 从 Server-Web 获取的预认证密钥
- `Ephemeral`: 设为 false，Agent 为持久节点

**主要功能**：

- `Start()`: 启动 Tailscale，连接到 Headscale
- `TailscaleIPs()`: 获取分配的 Tailscale IP（100.64.x.x）
- `Dial()`: 拨号到其他 Tailscale 节点
- `Listen()`: 监听端口，供其他节点访问

#### 5.2.1 内置 TCP 代理（替代 socat）

Agent 使用 Go 标准库实现 TCP 代理，无需额外的 socat 容器：

**TCP 代理核心逻辑**：

```txt
接收连接 → 拨号到目标 → 双向数据转发 (io.Copy)

优势：
- 单进程，无需协调多个容器
- Go 原生实现，性能更好
- 可以集成到现有 Agent 代码中
- 支持通过 gRPC 动态管理
```

**代理管理器设计**：

```txt
ProxyManager
├── proxies map[string]*TCPProxy    // 端口映射表
├── tsServer *tsnet.Server          // Tailscale 实例
│
├── Start(config ProxyConfig)       // 启动代理
│   ├── 在 Tailscale IP 上监听指定端口
│   ├── 接受连接后拨号到内网目标
│   └── 双向转发数据 (io.Copy)
│
├── Stop(name string)               // 停止代理
│   └── 关闭监听器，清理连接
│
└── List() []ProxyConfig            // 列出所有代理

ProxyConfig
├── Name        string   // 代理名称，如 "gateway-443"
├── ListenPort  int      // 监听端口，如 443
├── TargetAddr  string   // 目标地址，如 "192.168.1.1:443"
└── Status      string   // 运行状态
```

#### 5.2.2 gRPC 动态管理端口映射

通过现有的 Agent-Server gRPC 通道，Server 可以动态下发端口映射指令：

**新增 gRPC 消息定义**：

```txt
// 端口映射指令
ProxyCommand
├── action      string   // "start" | "stop" | "list"
├── name        string   // 代理名称
├── listen_port int      // 监听端口
├── target_addr string   // 目标地址 (内网 IP:端口)

// 端口映射状态上报
ProxyStatus
├── name        string   // 代理名称
├── listen_port int      // 监听端口
├── target_addr string   // 目标地址
├── status      string   // "running" | "stopped" | "error"
├── connections int      // 当前连接数
├── bytes_in    int64    // 入站流量
├── bytes_out   int64    // 出站流量
```

**动态管理流程**：

```txt
┌─────────────────────────────────────────────────────────────────────────────┐
```

#### 5.2.3 与现有 FRP 代理的对比

| 特性     | FRP 代理                | Tailscale + 内置 TCP 代理  |
| -------- | ----------------------- | -------------------------- |
| 容器数量 | 1 (Agent)               | 1 (Agent)                  |

| 动态管理 | gRPC 指令               | gRPC 指令（保持一致）      |
| 流量路径 | Agent → Server → Client | Agent ← Tailscale → Client |
| 加密     | TLS                     | WireGuard                  |
| P2P 直连 | ❌ 不支持               | ✅ 支持                    |

#### 5.2.4 Agent 启动流程

```txt
Agent 启动

    │       - 注册 Agent
    │       - 获取 Tailscale AuthKey
    │
    ├─► 2. 初始化 tsnet.Server
    │       - 设置 ControlURL (Headscale)
    │       - 设置 AuthKey

    │
```

### 5.3 Desktop 嵌入说明

Desktop 端同样使用 `tsnet.Server`，但配置略有不同：

**核心配置项**：

- `Hostname`: 使用用户名或设备名
- `Dir`: 用户目录下的状态文件
- `ControlURL`: 同 Agent
- `AuthKey`: 用户登录后从 Server-Web 获取
- `Ephemeral`: 设为 true，断开后自动清理设备记录
- `Logf`: 设为空函数，静默日志输出

**主要功能**：

- `Connect()`: 使用 AuthKey 连接到 Tailscale 网络
- `Disconnect()`: 断开连接并清理
- `Dial()`: 拨号到 Agent 或内网服务
- `LocalProxy()`: 创建本地代理端口，映射到远程服务

### 5.4 Server 端集成说明

Server 端不嵌入 Headscale，而是通过 HTTP API 调用：

**Headscale API 客户端功能**：

- `CreatePreAuthKey()`: 为用户创建预认证密钥，绑定用户和设备
- `ListMachines()`: 列出所有已注册设备
- `DeleteMachine()`: 删除设备（用户离职或设备注销时）
- `EnableRoute()`: 批准 Agent 广播的子网路由

**为什么不嵌入 Headscale**：

- Headscale 是独立项目，没有官方嵌入 API
- 通过 HTTP API 调用更灵活，解耦合
- 便于独立升级和维护 Headscale

### 5.5 身份验证流程

整个身份验证分为四个步骤：

**步骤 1: Desktop 用户登录（保持现有流程）**

Desktop 向 Server-Web 发送登录请求，包含 client_id 和 secret。Server-Web 验证用户身份后生成 JWT session_token 返回给 Desktop。此步骤与现有流程完全一致。

**步骤 2: Desktop 请求 Tailscale 接入（新增 API）**

Desktop 携带 session_token 调用新增的 `/api/v1/client/tailscale/auth` 接口。Server-Web 验证 JWT 有效性后，调用 Headscale API 为该用户创建预认证密钥（AuthKey）。AuthKey 绑定用户身份，设置过期时间，返回给 Desktop。

**步骤 3: Desktop 连接 Tailscale 网络**

Desktop 使用获取的 AuthKey 初始化 tsnet.Server，设置 ControlURL 指向 Headscale。tsnet 自动完成设备注册、密钥交换，获得 Tailscale IP（100.64.x.x）。此时 Desktop 已加入 Tailscale 虚拟网络。

**步骤 4: Desktop 访问内网服务**

Desktop 通过 tsnet.Dial() 拨号到 Agent 的 Tailscale IP 或内网 IP（通过子网路由）。连接优先尝试 P2P 直连，失败则通过 DERP 中继。数据通过 WireGuard 加密传输。

### 5.6 新增 API

**获取 Tailscale 认证信息**

- 路径: `POST /api/v1/client/tailscale/auth`
- 请求头: `Authorization: Bearer {session_token}`
- 响应字段:
  - `auth_key`: Tailscale 预认证密钥
  - `control_url`: Headscale 控制平面 URL
  - `expires_at`: 密钥过期时间

**断开 Tailscale 连接**

- 路径: `DELETE /api/v1/client/tailscale/disconnect`
- 请求头: `Authorization: Bearer {session_token}`
- 功能: 断开连接并在 Headscale 中清理设备记录

## 7. 使用场景

### 7.1 访问内部群晖 Drive Client

**前提**：

- 群晖 NAS IP: `192.168.1.100`
- Drive 端口: `6690`
- Agent 已广播路由: `192.168.0.0/16`

**配置步骤**：

1. Desktop 安装 Tailscale 并连接 Headscale
2. 确认路由已启用：
   ```bash
   tailscale status
   # 应显示 agent-internal 和子网路由
   ```
3. 配置群晖 Drive Client：
   - 服务器地址: `192.168.1.100`
   - 端口: `6690`
   - 直接使用内网 IP，无需端口映射

**访问路径**：

```
Desktop (100.64.0.3)
    → WireGuard隧道
    → Agent (100.64.0.1)
    → 子网路由
    → 群晖 (192.168.1.100:6690)
```

### 7.2 访问内部 K8S Service

**前提**：

- K8S Service CIDR: `10.96.0.0/12`
- K8S Pod CIDR: `10.244.0.0/16`
- 示例服务: `my-app.default.svc.cluster.local` → `10.96.100.50:80`

**方案 A: 通过 Agent 子网路由**

```bash
# Agent 广播 K8S 网段
tailscale up --login-server=https://hs.your-domain.com \
  --advertise-routes=10.96.0.0/12,10.244.0.0/16,192.168.0.0/16
```

访问方式：

```bash
# 直接访问 ClusterIP
curl http://10.96.100.50:80

# 或配置 DNS 后访问
curl http://my-app.default.svc.cluster.local
```

**方案 B: 在 K8S 中部署 Tailscale Operator**

```yaml
# tailscale-operator.yaml
apiVersion: v1
kind: Secret
metadata:
  name: tailscale-auth
  namespace: tailscale
stringData:
  TS_AUTHKEY: "xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx"
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: tailscale-subnet-router
  namespace: tailscale
spec:
  replicas: 1
  selector:
    matchLabels:
      app: tailscale-subnet-router
  template:
    metadata:
      labels:
        app: tailscale-subnet-router
    spec:
      containers:
        - name: tailscale
          image: tailscale/tailscale:latest
          env:
            - name: TS_AUTHKEY
              valueFrom:
                secretKeyRef:
                  name: tailscale-auth
                  key: TS_AUTHKEY
            - name: TS_EXTRA_ARGS
              value: "--advertise-routes=10.96.0.0/12,10.244.0.0/16"
            - name: TS_USERSPACE
              value: "false"
          securityContext:
            capabilities:
              add:
                - NET_ADMIN
```
